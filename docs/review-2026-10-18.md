# Review of the ork spec, 2026-10-18

A critical pass over PROJECT.md, docs/ and the adj records, checked against
the sibling repos and the installed tools (slicer 1.15.0, adj 0.1.0). Each
finding has a severity, the evidence, and a suggested change. Nothing here
is applied; the owner picks.

Severity: **high** = changes the direction or blocks v1; **medium** = a
real gap to close before implementation; **low** = a correction or a
polish.

## Direction

### 1. ork is three products in one. Ship them in order. (high)

PROJECT.md has four capability goals: a cross-project dashboard, a roadmap
editor, a decision manager, and a relay launcher. Each is a different kind
of work (read-only views, write adapters, process supervision), and the
launcher alone carries most of the risk (findings 4-7). Building all four
before anything is usable is the main way this project fails to ship.

Suggestion: make `scope.v1` a phased order and decide it now:

1. **Read-only dashboard.** Projects, roadmaps, decisions, live relays from
   the ledger. No writes, so no conflict handling. This already answers "what
   needs me now" across projects, which nothing provides today.
2. **Decisions.** `adj` has five write verbs and millisecond calls; the
   inbox is the owner's own queue. Cheapest write surface, highest daily
   value.
3. **Roadmap edits.** Reorder, start, park, retire; open `slicer tui` for
   the rest (`ui.slicer-tui`).
4. **Launch and supervise.** Only after 1-3 are in daily use, and after
   finding 4 is verified.

Each phase is usable on its own. Record the order in `scope.v1` as options
`phase-1-readonly` ... and decide it.

### 2. "Owner-attended" needs a precise meaning. (high)

PROJECT.md lists "no unattended runs" as a non-goal and, in the same
document, has ork launch a headless orchestrator that runs implementer,
reviewer and gate on its own until the run report. Between the owner's
launch approval and the report, nobody attends. The agents repo allows
unattended runs only inside agentbox (`agents/ROADMAP.md:71-76`,
`agents/CONTAINERS.md`).

This is not a contradiction once stated plainly, but today the docs read as
one. Suggestion: define *attended* as "the owner approves launch, accepts
or rejects the gate result, and approves landing; between those points the
roles run autonomously inside one slice worktree, with the permission mode
the lineup names." Then decide whether an ork-launched orchestrator must run
inside agentbox (the agents repo's current rule) or may run on the host.
That is a new adj question: `launch.sandbox`.

### 3. Three overlapping orchestration plans exist. Reconcile them. (high)

- agents `N6`: "a scripted cross-vendor orchestrator that commits only on a
  run branch ... runs unattended only in agentbox" (`agents/ROADMAP.md:71`).
- agents `implementation-plan.md:660`: "Scripted orchestrator: replace the
  orchestrator skill with a small program that runs the state machine and
  calls each role headlessly ... Build this only after the skill version is
  stable."
- ork goal 4.

ork is that program. If the owner agrees, say so in both repos: an agents
ROADMAP note that N6's scripted orchestrator is ork, and a line in ork's
PROJECT.md. Otherwise two tools will be specified for the same job. This
folds into `boundary.agents-scripts`; the record should gain the option
"ork is N6".

Similarly, adj `S19` (TUI or static HTML inbox, open) overlaps ork's
Decisions screen. If ork phase 2 is the TUI inbox, S19 can be narrowed to
the static HTML page or retired. Note it on S19 when the owner decides.

## Launching

### 4. Unverified: can a headless orchestrator spawn its roles? (high)

The design launches the orchestrator with `claude -p` (`launch.vendor`
recommendation). The orchestrator's whole job is to spawn and wait on role
subagents. Nothing in the three repos shows a headless `claude -p` session
using the Agent tool; every trial ran the orchestrator as a subagent of an
interactive session (`slice-relay.md:113-116`). For Grok the repo records
that subagents cannot nest, so the orchestrator must be top-level
(`agents/multi-agent-workflows/info/review-feedback.md:79`). Headless makes
the orchestrator top-level, which helps, but whether the harness allows
subagent spawns, foreground waits and SendMessage resumes in print mode is
unknown.

Suggestion: before deciding `launch.vendor`, run one experiment: a `claude
-p` session in a throwaway worktree briefed with `slicer ai
relay-orchestrator` on a trivial slice, with `--output-format json`, and
check that role subagents ran and a run report came back. Record the result
as the record's context. If it fails, the fallback design is the agents
repo's own: ork runs the state machine and calls each role headlessly
(`implementation-plan.md:660`), which removes the orchestrator agent
entirely and makes ork's stage table real rather than derived.

### 5. The launcher depends on the agents repo's installed agent types. (medium)

The orchestrator brief says to run as agent type `relay-orchestrator`
"where the harness has one installed" (`slicer ai relay` Setup). Those
files are generated by `gen-relay-agents.sh` and linked into
`~/.claude/agents` (`slice-relay.md:45-56`). ork has no way to know they are
current. Suggestion: ork's doctor checks the installed role files' `Expects:
relay vN` line against `slicer ai relay --json`'s version, as the agents
repo doctor does, and refuses to launch on mismatch. Add to
`docs/dashboard.md` Setup flow, step 2.

### 6. Process supervision is under-specified. (medium)

`docs/state.md` keeps a `pid` and `exit`. Not covered: ork restarting while
runs are live (reconcile from pidfiles and the ledger), orphaned role
processes when the orchestrator dies, a run that never ends (the ledger
marks a run stale after 30 minutes without an event), stopping a run cleanly
(kill the process group, then `relay-run end --close-steps fail`?), and the
cost of a run (no token figures anywhere; the trials measured cost from the
weekly `/usage`, `nested-relay.md:95-97`).

Suggestions: launch in its own process group and store the group id; on
start, reconcile every run record against live processes and the ledger;
capture the headless JSON output and read its usage fields into the run
record so the Relays screen shows tokens and elapsed time per run; define
"Stop" as an owner-confirmed action with a recorded reason.

### 7. Two controllers for one run. (medium)

A relay started by hand in a Claude outer session and one ork launched both
appear in the ledger. Both the session and ork could run `relay-run end`,
file notes, or land. Suggestion: a rule in boundaries.md: ork acts (end,
note, land) only on runs in its own run records; everything else is
view-only, with a "started elsewhere" marker. The outer session keeps
owning the runs it started.

### 8. Worktree and branch naming is per project. (low)

adjudicate uses `.worktrees/sNN` on branch `sNN`
(`adjudicate/.slicer/render/slices/S38.md:72`); `slicer ai relay-brief`
takes `--worktree` and `--branch` as arguments, so slicer does not fix the
scheme. Add `worktree_pattern` and `branch_pattern` to `projects.json`
(default `.worktrees/{id}` and `{id}`), detected or asked at registration.

## Dashboard and data

### 9. Live agent progress is thinner than the goal implies. (medium)

Goal 1 promises "every agent and subagent ... with its stage and
progress". The only cross-session source is slicer's relay-run ledger, and
recording there is advisory: "a failed `relay-run` call never stops the
relay" (`slicer ai relay-orchestrator`). The ledger gives one row per step
with role, agent, vendor, model, phase and task (fields checked on the
slicer repo's own 76 runs), nothing inside a step. For runs ork launches,
the captured output adds real progress; for runs started elsewhere, the
ledger is all there is.

Suggestion: state this in dashboard.md so the Relays screen is designed for
what the ledger has (step list, phase, elapsed since `updated_at`, stale
flag) and treats per-step progress as an ork-launched-only extra. Consider a
slicer feature request later: an optional `--note` on heartbeats so a role
can report "12/21 tests green" without a new step.

### 10. The polling risk is overstated; use what slicer already has. (low)

PROJECT.md Risks says each slicer call starts a Python interpreter and may
be slow. Measured: `slicer list --json --lean` on the slicer repo takes
about 0.1 s; `adj inbox --json` about 3 ms. Polling five projects every few
seconds is fine. Replace the risk with the actual tools: `slicer status -r`
reports every project under a directory in one call (exists in 1.15.0), and
`slicer log --since TIMESTAMP --json` detects changes without re-reading the
queue. The Overview can use the first; refresh can use the second.

### 11. Some adj features the design relies on are unreleased. (low)

`adj repos`, `adj inbox --all` and `adj list --ref` are done in adjudicate's
source (S18, S38 done on 2026-10-18) but not in the installed 0.1.0.
dashboard.md marks one of them. Either pin ork to adj 0.2.0 or have ork
iterate its own registry and call `adj inbox --json --root P` per project,
which needs nothing unreleased. The second is simpler and keeps the registry
in one place (ork's), so prefer it and drop the `adj repos` dependency.

### 12. The registry duplicates `adj repos`. Decide which is canonical. (low)

Once adj 0.2.0 ships, there will be two lists of projects: ork's
`projects.json` and adj's `$XDG_CONFIG_HOME/adjudicate/config.json`. ork's is
the superset (slicer-only projects such as DataBall have no adj). Suggestion:
ork's registry is canonical; ork never writes adj's list and ignores it.

## State

### 13. Fine as scoped; two gaps. (low)

- Run records carry `stage` and `report`, derived data that can go stale.
  That is acceptable for crash recovery, but mark them as "last seen" in the
  UI and recompute from the ledger on every refresh.
- No schema for `ui.json`. Not needed yet; say it is free-form until v1.

## Contract coupling

### 14. ork would follow a prose contract with code. (medium)

`slicer ai relay` prints prose for a model to follow. ork would implement
the outer-session half of it (Setup, Order, report checks) in Go. The
version check protects against silent drift, but every contract bump then
needs an ork release to read a new prose rule. Suggestion: a slicer feature
request, filed as a slicer item, for the machine-readable parts of the
contract in `ai relay --json`: version, the Setup fields, the Order steps as
an array, the report line names and the `OUTCOME` values. ork then validates
reports against slicer's own description. Check first what `slicer ai relay
--json` already carries; the ai.py comment says the version is in it.

## UI

### 15. Add notifications. (medium)

With four relays running across projects the owner is not watching the
TUI. The screens have a "needs you" count but no way to reach the owner.
Add a terminal bell and, where available, a desktop notification when a run
reaches an approval point, stops, or goes stale. This is cheap and is most
of the "ease of use" value for parallel work. New adj question or a line in
dashboard.md Principles.

### 16. Do not rebuild slicer's editor. (medium)

slicer's TUI already edits every field, section, note and prose block, and
has a roadmap wizard (`slicer/docs/tui.md`). Reimplementing that in ork is a
large, duplicated surface that drifts as slicer changes. The `ui.slicer-tui`
recommendation ("both") is right; make it concrete: ork does reorder, start,
park, unpark, retire, decide, and launch. Everything else is one key that
suspends ork and runs `slicer tui --root P`. Move this from an open question
to a decision.

### 17. Keyboard map, themes and the monochrome rule are unspecified. (low)

Fine for now. Draft them with the first prototype, not before.

## Engineering

### 18. No test strategy. (medium)

Nothing says how ork is tested without live agents. Suggest, in AGENTS.md
once code starts: adapters are tested against recorded CLI output fixtures
(JSON captured from `slicer ... --json` and `adj ... --json`, refreshed per
tool release); the launcher has a `--dry-run` that prints every command
instead of running it; TUI models are tested as pure state transitions
(Bubble Tea's model/update design allows this). Keep real-agent runs for a
manual checklist.

### 19. Dependency licenses are not verified. (low)

PROJECT.md names Bubble Tea, Lip Gloss and Bubbles with "licenses to be
verified". They cannot be verified offline from this workspace. Do it when
`ui.framework` is decided, from each repository's LICENSE file, and record
the result in the record's rationale. A FLOSS alternative to compare is
`tview` (also a single Go dependency).

### 20. License choice is unconstrained by the siblings. (low)

ork only runs `slicer` and `adj` as processes and links no code from either,
so neither Apache-2.0 nor GPL-3.0-or-later is forced. The choice is policy
only. Decide `license.choice` whenever convenient.

### New risks raised by the decisions

- **All three vendors and automatic fallback in v1.** This is the largest
  scope item and rests on vendor behavior nobody has measured. The vendor
  spike comes first. If one vendor's CLI lacks resume, usage or streaming,
  narrow v1 for that vendor rather than delay everything.
- **Split and slivers in v1.** They add parallelism inside a slice on top of
  parallelism across slices. Build them last (design.md, Build order 8).
  Keep them cuttable if v1 runs long.
- **ork's role prompts are now a third copy of relay rules,** next to
  slicer's contract and the agents repo files. The mitigations are the
  version pin, `ork roles print` as the agents repo's source, and the slicer
  JSON item. This needs watching at every contract bump.
